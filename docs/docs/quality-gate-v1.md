# Quality Gate v1 — WhereToGo

## 1. Назначение

Quality Gate v1 определяет минимальные требования к качеству программных изменений проекта WhereToGo перед их объединением с основной веткой. Проверки разделены на быстрый автоматизированный контур и расширенный контур анализа. Отдельно выделена процедура Code Review.

Автоматические проверки запускаются GitHub Actions workflow `CI Checks` при `pull_request` и `push` в ветки `main` и `master`, если изменение затрагивает каталоги `android/`, `backend/` или `.github/`. Также workflow можно запустить вручную (`workflow_dispatch`). Изменения только в `docs/` текущими фильтрами путей не запускают workflow.

## 2. Критерии быстрого контура

| Критерий | Условие прохождения | Действие при нарушении | Контур | Основание (риск) |

| Сборка и тесты Backend | Задание `build` завершилось успешно | Считать проверку неуспешной; исправить ошибку компиляции, тестов или сборки | Быстрый | Риск регрессии и нарушения серверной логики |

## 3. Процедурный критерий

| Критерий | Условие прохождения | Действие при нарушении | Контур | Основание (риск) |
|---|---|---|---|---|
| Code Review | Изменение рассмотрено другим участником команды; замечания обработаны; получено одобрение, когда оно требуется правилами проекта | Не принимать изменение до завершения проверки | Процедурный | Риск пропуска логических ошибок и проблем требований, которые не обнаруживаются автоматическими проверками |

## 5. Реализация проверок в CI

В workflow `.github/workflows/ci.yml` настроены следующие задания:

- `Unit tests` — запускает `./gradlew testDebugUnitTest --stacktrace` в каталоге `android/` и сохраняет отчёты тестирования.
- `Android Lint` — запускает `./gradlew lintDebug --stacktrace` в каталоге `android/` и сохраняет отчёт Lint.
- `Build debug APK` — запускает `./gradlew assembleDebug --stacktrace` и сохраняет собранный APK.
- `Build Backend (Gradle)` — запускает `./gradlew build --stacktrace` в каталоге `backend/`, затем выполняет Backend Quality Gate.
- `Secrets scan (gitleaks)` — выполняет проверку репозитория на наличие секретов с помощью Gitleaks.

Backend Quality Gate использует скрипт `.github/scripts/check-pmd-quality-gate.ps1`. Скрипт читает XML-отчёт `backend/build/reports/pmd/main.xml`. Если отчёт отсутствует или содержит блокирующие нарушения PMD с приоритетом 1–2, проверка завершается с ошибкой. Нарушения с приоритетом 3 не блокируют прохождение Quality Gate и могут быть дополнительно рассмотрены разработчиком.

В конфигурации Gradle для PMD установлено `ignoreFailures = true`, поэтому обнаруженные нарушения не останавливают формирование отчёта. Их обработка выполняется отдельным скриптом Quality Gate после формирования XML-отчёта.

## 6. Ограничения и условия применения

1. Успешное завершение задания GitHub Actions показывает, что соответствующая автоматическая проверка прошла. Для фактической блокировки слияния при неуспешной проверке необходимо отметить требуемые проверки как обязательные в настройках защиты целевых веток GitHub.
2. Требование Code Review является процедурным. Для его автоматического контроля необходимо настроить правила защиты веток и обязательное одобрение Pull Request.
3. В текущем workflow Android Lint запускается как общая проверка. Отдельный скрипт, который извлекает только `DefaultLocale` из SARIF и самостоятельно блокирует CI по этому идентификатору, не настроен. Поэтому отсутствие `DefaultLocale` контролируется при анализе отчёта Lint, а не отдельным специализированным Quality Gate.
4. Расширенный анализ предупреждений предполагает проверку отчётов разработчиком. Не каждое предупреждение автоматически является блокирующим нарушением.
5. Workflow запускается при изменениях в `android/`, `backend/` и `.github/`. Если требуется проверять изменения документации, путь `docs/**` следует добавить в фильтры `paths`.

## 7. Итог

Quality Gate v1 объединяет проверки Android, Backend и безопасности в едином CI-процессе, дополняя их процедурой Code Review и расширенным анализом предупреждений. Такой подход позволяет обнаруживать часть технических проблем до слияния изменений и снижает риск попадания дефектов и секретов в основную ветку проекта.
