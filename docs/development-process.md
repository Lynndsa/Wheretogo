# Правила разработки Wheretogo

## 1. Ветки

- Основная ветка проекта — `master`.
- Прямые изменения в `master` запрещены.
- Новые функции, исправления и документация разрабатываются в отдельных ветках - новая ветка создается из ветки `master` с названием задачи.
- Изменения попадают в `master` только через Pull Request (PR).

## 2. Правила оформления Pull Request

Каждый Pull Request должен включать:
* Сжатое описание внесенных правок.
* Ссылку на соответствующую задачу (Issue), если PR закрывает ее.

В PR запрещено добавлять посторонние изменения, временные и сгенерированные файлы сборки, а также конфиденциальные данные (секреты).

## 3. Автоматизированное тестирование и CI

Проверка кода автоматизирована через GitHub Actions и запускается при создании PR или отправке новых коммитов в него.

* **Текущий этап:** автоматизация контролирует успешность сборки проекта.
* **Планы:** внедрение автоматических тестов в pipeline GitHub Actions по мере разработки компонентов.
* **Правило слияния:** слияние PR в ветку `master` возможно только при успешном прохождении всех обязательных проверок, заданных в правилах защиты веток.

## 4. Независимое review

- Значимые изменения проверяет участник команды, который не является автором PR.
- Проверяющий оценивает логику, соответствие требованиям, обработку ошибок и безопасность.
- Одобрение должно быть получено до слияния.
- После существенных новых изменений PR повторно проверяется.
- Настройки защиты ветки изменяет участник с соответствующими правами.

## 5. Защита основной ветки (`master`)

- запрет прямого push;
- обязательный PR;
- обязательные статусные проверки;
- обязательное одобрение другим участником.


## 6. Критерии готовности задач (Definition of Done)

Пул-реквест считается завершённым и готовым к слиянию при соблюдении следующих условий:

- [ ] Чётко определена решаемая задача или реализуемое требование.
- [ ] Проведены все актуальные проверки, а их результаты открыты для команды.
- [ ] Описана методика проверки изменённого функционала/поведения.
- [ ] Актуализированы связанные инструкции, документация, конфигурационные файлы и спецификации.
- [ ] Проверено отсутствие секретов, токенов и паролей в коде, конфигурациях и журналах логов.
- [ ] Получено независимое перекрёстное рецензирование (Code Review) для всех значимых правок.
- [ ] Все ключевые замечания рецензента полностью устранены либо согласованно закрыты.

> **Примечание по проверкам:** Если автоматические тесты для данного модуля ещё не написаны, проведите доступную ручную/локальную проверку и зафиксируйте её результаты в PR. В будущем новые тесты должны быть обязательно интегрированы в pipeline GitHub Actions.
## 7. Значимые изменения

К значимым изменениям Wheretogo относятся:

- изменение архитектуры Android-клиента или Spring Boot backend;
- изменение API-контрактов и формата передаваемых данных;
- изменение существенных требований к приложению;
- изменение структуры базы данных;
- изменение конфигурации сборки Android или backend;
- изменение процесса сборки и поставки приложения;
- исправление критических дефектов;
- добавление мер защиты, например проверки доступа к пользовательским данным.

Такие изменения требуют независимого review участником команды, который не является автором Pull Request. До слияния необходимо проверить корректность решения, обработку ошибок, безопасность и соответствие требованиям.

## 8. Пример содержательного замечания при review

**Задача:** реализовать добавление интересных мест в список «Избранное» в приложении Wheretogo.

**Замечание проверяющего:**

> Не определено поведение при повторном добавлении одного и того же места в избранное (например, при быстром повторном нажатии на «сердечко» или сетевом сбое). В результате одна локация может дублироваться в списке пользователя, а бэкенд на Spring Boot может возвращать ошибку уникальности базы данных (`DataIntegrityViolationException`). Нужно уточнить ожидаемое поведение и добавить проверку повторного добавления.

**Ожидаемое решение:**

1. **Уточнить требование:** одно место не должно дублироваться в списке избранного одного пользователя. Повторный запрос должен обрабатываться идемпотентно — сервер возвращает успешный статус без создания дубликата.
2. **Реализовать проверку:** на стороне Spring Boot добавить составной уникальный индекс `(user_id, place_id)` в СУБД и проверку перед записью, а на Android-клиенте — мгновенную блокировку повторного нажатия UI-кнопки.
3. **Добавить автоматический тест:** написать юнит/интеграционный тест для проверки повторного сохранения одной и той же локации.
4. **Повторно проверить изменение** и устранить замечание до слияния Pull Request в ветку `master`.

---

*Качество review определяется тем, насколько замечания выявляют реальные проблемы и помогают их устранить, а не количеством комментариев или одобрений.*
## 9. Применение DoD в Wheretogo

При реализации новой функции, например авторизации пользователя или отображения мест на карте, разработчик создаёт Issue с критериями приёмки, выполняет изменения в отдельной рабочей ветке (`create-add-api`, `test_map`), запускает локальную сборку и доступные проверки, а затем открывает Pull Request.

GitHub Actions выполняет настроенные автоматические проверки (сборка `android/` и `backend/`, запуск тестов). Второй участник команды проверяет значимые изменения (контракты API, навигацию, структуру БД), оставляет замечания при необходимости и подтверждает готовность после их устранения.

Слияние в `master` выполняется только после прохождения CI-чеков и разрешения всех возникших конфликтов слияния.
