# Исходное состояние и ранние ограничения безопасности — Wheretogo

Связано с [requirements.md](requirements.md) (FR-01…FR-09, NFR-01…NFR-03).

## 1. Как проверяющий получит нужное состояние

| Что | Как получить                                                                                                                                                                     |
|---|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| База данных | База данных развернута на удаленном сервере / облачной платформе (например, PostgreSQL/H2 на Render / TiDB Cloud). Со стороны проверяющего дополнительных действий не требуется. |
| Запуск backend (Spring Boot) и Android-клиента | Android-клиент собирается из монорепозитория (`android/`) через Gradle. Запуск Spring Boot осуществляется локально из репозитория (?)                                            |
| Учебные учётные записи | Два тестовых пользователя (обычный пользователь и гостевой режим), созданные через миграции или скрипт бэкенда; пароли в репозитории не хранятся.                                |
| Внешний API (карты и музеи) | Учебный режим: фиксированный набор точек и маршрутов в тестовой базе данных, чтобы проверка не зависела от личных ключей разработчиков и доступности внешних сервисов.           |

**Набор тестовых сценариев** (покрывает критерии из `requirements.md`):

- корректная точка музея с координатами, графиком и описанием (FR-03, FR-06);
- карточка локации без детального описания или с отсутствующими опциональными полями (FR-05);
- сценарий недоступности внешнего API — переключение на локальную БД (fallback) при отключенной сети (FR-05, FR-09);
- сценарий пустой выдачи — в выбранном радиусе или категории нет объектов (FR-09);
- сценарий недоступного бэкенда — остановленный сервер или обрыв связи (FR-09).

**Для будущих проверок:** тестовые данные для проверки идемпотентности избранного (FR-04) и для замеров отклика карты (NFR-01, нужное число точек).

## 2. Ранние ограничения безопасности

| Вопрос | Ответ |
|---|---|
| Важно сохранить или ограничить | Учётные данные и профиль пользователей, историю посещений и избранное, ключи внешних API (карт), пароль/токен подключения к БД |
| Откуда приходит недоверенный ввод | Поля формы регистрации, входа и профиля; ответы внешних API карт и музеев (тексты, координаты, отсутствующие или неожиданные поля) |
| Кто должен иметь доступ к существенным действиям | Избранное и личный кабинет — только владелец аккаунта (через JWT-токен); БД — только Spring Boot бэкенд |
| Реалистичный ущерб | Несанкционированный доступ к чужому профилю или избранному; утечка ключа API карт или пароля БД через публичный репозиторий; краш Android-клиента из-за некорректного JSON-ответа от бэкенда |
| Где хранится конфигурация с секретами и что нельзя выводить в журнал | Переменные окружения и GitHub Secrets, а также локальный файл `local.properties` (не попадают в Git); в журналы и сообщения об ошибках запрещено выводить пароли, JWT-токены и ключи API |


## 3. Планируемая проверка

| Требование | Когда и как проверим |
|---|---|
| NFR-02 | Регулярный поиск секретов в репозитории (`git grep`, сканеры в CI) при каждом PR и перед сдачей |
| NFR-03 | После реализации авторизации: HTTP-запрос к чужому избранному или профилю без валидного токена должен вернуть отказ (`HTTP 401/403`); в БД пароли хранятся исключительно в захешированном виде |
| FR-05 / FR-09 | Ручной прогон сценариев сбоя сети (отключение интернета на эмуляторе) для проверки fallback-логики и обработки ошибок |
