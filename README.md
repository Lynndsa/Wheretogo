
# Куда сходить

## 1. Название и команда

**«Куда сходить»** — Android-приложение для поиска достопримечательностей Санкт-Петербурга, просмотра информации об интересных местах и планирования прогулок по городу.

**Команда:** Андрей Гуляев, Лада Романова.

**Технологии:** Kotlin, Jetpack Compose, Java, Spring Boot, MySQL.

## 2. Пользователь

Основной пользователь — человек, который хочет познакомиться с достопримечательностями Санкт-Петербурга, найти интересные места для посещения и самостоятельно спланировать прогулку по городу.

Приложение ориентировано как на жителей города, так и на туристов.

## 3. Проблема

При планировании прогулок пользователю приходится искать достопримечательности на разных сайтах и картах, отдельно изучать описание каждого места, искать адреса и самостоятельно составлять маршрут.

Это усложняет выбор интересных мест и планирование прогулок, особенно если пользователь плохо знаком с городом.

## 4. Текущий способ работы

Сейчас пользователь может искать достопримечательности через картографические сервисы, туристические сайты и другие источники информации. Для планирования прогулки ему приходится самостоятельно сравнивать места, сохранять интересные варианты и определять последовательность посещения.

Приложение «Куда сходить» призвано объединить поиск достопримечательностей, просмотр информации о них и планирование прогулок в одном интерфейсе.

## 5. MVP (Minimum Viable Product)

MVP — минимально жизнеспособная версия приложения, включающая основные функции, необходимые для решения проблемы пользователя.

В MVP планируется реализовать:

* регистрацию и авторизацию пользователей;
* отображение карты Санкт-Петербурга;
* поиск и отображение достопримечательностей;
* просмотр карточек мест с названием, описанием, адресом и координатами;
* получение информации о достопримечательностях через внешние API;
* добавление мест в избранное и просмотр сохранённых достопримечательностей.

Дополнительные возможности, такие как аудиогид, расширенное управление маршрутами и полноценный офлайн-режим, могут быть реализованы на следующих этапах разработки.

## 6. Собственная логика

Команда самостоятельно разрабатывает Android-приложение и серверную часть на Spring Boot.

Собственная логика проекта включает:

1. **Обработка данных достопримечательностей.** Получение информации из внешних API, преобразование ответов и подготовка данных для отображения в Android-приложении.
2. **Отображение мест на карте.** Использование координат достопримечательностей для размещения объектов на интерактивной карте.
3. **Работа с карточками.** Отображение названия, описания, адреса, категории и доступных ссылок на дополнительные сведения.
4. **Работа с избранным.** Добавление и удаление достопримечательностей из списка избранного пользователя.
5. **Построение маршрутов.** Планируемая реализация формирования маршрутов из выбранных достопримечательностей.
6. **Локальное хранение данных.** Планируется сохранять необходимые данные на устройстве для доступа к ранее загруженной информации без подключения к интернету.

Взаимодействие с внешними API выполняется через серверную часть, которая обрабатывает полученные данные и передаёт их Android-клиенту.

## 7. Модуль-кандидат

**Модуль получения и отображения достопримечательностей.**

Модуль предназначен для получения информации о местах через серверную часть и отображения результатов в приложении.

Модуль можно отдельно проверять и тестировать:

* корректно ли выполняются запросы к серверу;
* обрабатываются ли полученные данные;
* отображаются ли достопримечательности с правильными координатами;
* корректно ли обрабатываются отсутствующие описания, фотографии и адреса;
* как приложение реагирует на ошибки сети и недоступность внешнего API;
* соответствуют ли данные в карточках полученному ответу сервера.

В дальнейшем отдельным модулем для тестирования может стать построение маршрутов прогулок.


## 8. База данных

Для хранения данных приложения используется реляционная база данных MySQL. Структура базы данных включает таблицы для пользователей, настроек, достопримечательностей, избранного и маршрутов.

### Структура базы данных

* **users** — учётные записи пользователей. Содержит идентификатор пользователя, логин и пароль.
* **user_information** — дополнительная информация о пользователях: имя, фамилия, номер телефона и электронная почта.
* **user_settings** — настройки пользователя, включая громкость звука и тему оформления.
* **attractions** — информация о достопримечательностях, включая название и ссылку на аудиофайл.
* **custom_places** — дополнительные места с названием, описанием, адресом, координатами, категорией, изображением и ссылкой на сайт.
* **favorites** — связь пользователей с достопримечательностями, добавленными в избранное.
* **routes** — готовые и пользовательские маршруты. Содержит название, описание, автора маршрута и признак публичности.
* **route_attractions** — связь маршрутов с достопримечательностями и порядок их посещения.
* **favorite_routes** — связь пользователей с маршрутами, добавленными в избранное.

### Основные данные

Для пользователей предусмотрены:
* `id_user` — идентификатор пользователя;
* `login` — логин;
* `password` — пароль.

Для достопримечательностей в таблице `attractions` предусмотрены:
* `id_attraction` — идентификатор достопримечательности;
* `name` — название;
* `audio_url` — ссылка на аудиофайл.

Для дополнительных мест в таблице `custom_places` предусмотрены:
* `id_custom_place` — идентификатор места;
* `name` — название;
* `description` — описание;
* `address` — адрес;
* `latitude` и `longitude` — географические координаты;
* `category` — категория места;
* `image_url` — ссылка на изображение;
* `website_url` — ссылка на сайт;
* `id_attraction` — идентификатор связанной достопримечательности.

### Связи между таблицами

* Пользователь связан с дополнительной информацией и настройками.
* Пользователь может сохранять достопримечательности и маршруты в избранном.
* Пользователь может создавать маршруты.
* Маршрут может включать несколько достопримечательностей.
* Для определения порядка посещения достопримечательностей используется поле `position` в таблице `route_attractions`.
* Дополнительные места могут быть связаны с достопримечательностями.

Структура базы данных позволяет хранить пользовательские данные, настраивать приложение, управлять избранным и организовывать маршруты прогулок.

## 9. Внешние ресурсы и инструменты

Для разработки и работы приложения используются:

* **Android Studio** — среда разработки Android-клиента;
* **Kotlin** — язык программирования Android-приложения;
* **Jetpack Compose** — создание пользовательского интерфейса;
* **Java** — язык программирования серверной части;
* **Spring Boot** — разработка серверного API;
* **MapLibre** — отображение интерактивной карты;
* **внешние API** — получение географических данных и информации о достопримечательностях;
* **H2** — временная база данных для разработки backend;
* **MySQL** — планируемая база данных для постоянного хранения данных;
* **GitHub** — хранение исходного кода и совместная разработка.

Разработка ведётся на компьютерах команды под управлением Windows 11. Для тестирования Android-клиента используется физическое устройство или эмулятор.

## 10. Ограничения

* Команда состоит из двух человек.
* Проект разрабатывается в рамках учебной практики и семестрового проекта, поэтому сроки разработки ограничены.
* Полнота информации о достопримечательностях зависит от используемых источников данных.
* Для отдельных мест могут отсутствовать фотографии, описания, адреса или ссылки.
* Доступность информации зависит от работы внешних API и серверной части.
* Получение новых данных требует подключения к интернету.
* Полноценный офлайн-режим зависит от реализации локального хранения данных и предварительной загрузки необходимых ресурсов.
* Некоторые функции могут оставаться планируемыми до завершения соответствующих этапов разработки.

## 11. Критерий достижения цели проекта

Основная цель проекта будет достигнута, когда пользователь сможет открыть карту Санкт-Петербурга, находить достопримечательности, просматривать подробную информацию о выбранных местах и сохранять понравившиеся варианты.

Приложение должно корректно взаимодействовать с серверной частью, обрабатывать полученные данные и предоставлять понятную обратную связь при возникновении ошибок.
